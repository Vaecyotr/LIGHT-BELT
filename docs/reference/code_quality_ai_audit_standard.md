# 高质量代码标准与 AI 代码审查协议

版本：1.0（2026-11-06）  
适用范围：多语言、跨层软件项目；可按项目实际技术栈、硬件约束与部署方式裁剪。

## 1. 目的和使用边界

这份标准回答三个问题：什么值得称为好代码、怎样判断现有代码是否存在质量问题、怎样让 AI 稳定执行有证据的审查。

它既用于存量代码库的基线审查，也用于日常变更审查和后续改进验收。它不是语言格式规范，不规定统一的架构形式，也不要求把所有启发式建议当作必须通过的检查。

本文件独立于任何具体仓库。针对某仓库使用时，必须先以真实需求、协议、源码、部署约束和测试结果建立项目上下文；不得把本文中的假想示例当成仓库事实。

**核心标准：在满足正确性、安全性与运行约束的前提下，让维护者能够以合理成本定位、理解、修改、验证和运行软件。**

代码质量是一组需要权衡的性质，不是行数、注释率、覆盖率、复杂度或某个工具分数。任何发现均应描述实际损害、可能损害或可验证的维护成本。

## 2. 质量原则及判断方法

### 2.1 正确性与行为契约

- 实现符合实际需求、输入输出契约和系统边界；不仅正常路径正确，异常、边界和恢复路径也明确。
- 设计说明、代码和测试对关键行为一致；测试验证用户可见或调用者可观察的行为，不仅锁定内部实现。
- 区分“执行成功”“收到确认”“状态已经持久化”等不同事实；超时或丢失响应不等同于操作未执行。
- 在存在状态、重试、并发、跨进程通信时，验证幂等性、顺序、取消、超时以及重复消息的语义。

**审查证据**：需求或协议条款、调用链、接口定义、反例测试、运行日志、复现步骤。

### 2.2 可读性、命名与注释

- 名称准确表达职责；在所在作用域内足够明确，避免不必要的重复前缀、泛化名称和没有含义的缩写。
- 同一概念使用一致的术语。`load`、`fetch`、`parse`、`validate`、`apply` 等动词应对应真实行为，不用 `handle`、`process` 掩盖重要差异。
- 函数有可辨认的主流程；适度拆分可以帮助理解，机械地把函数切成很短的小片段也会降低可读性。
- 注释优先说明**原因、约束、风险、非显而易见的算法以及外部事实依据**。如果注释只是在翻译代码，优先改名或简化代码。
- 公共接口文档说明用途、输入、输出、失败模式和约束；长期存在的设计决定应留下简短依据，避免记录聊天过程或临时修改经历。
- 不保留明显过时的注释、废弃代码块、虚构的安全说明或“为了稳妥”等无法验证的理由。

**辨别示例**：

```python
# 没有信息增量的注释
# 把音量限制到 100
volume = min(volume, 100)

# 有依据时才保留的注释
# 此协议拒绝超过 100 的音量值；发送前裁剪可避免整条命令失败。
volume = min(volume, 100)
```

后一条注释只有在协议确实这样规定时才成立。猜测性的理由不能写成事实。

### 2.3 目录、模块和职责边界

- 通过功能、领域或稳定的系统边界组织代码；维护者根据名称和调用关系能够合理推断实现位置。
- 同一行为应有清楚的主入口、执行位置和状态所有者；避免相同功能在不同目录各有一套实现。
- 一个模块应承担有内在关联的职责；避免“全能管理器”，也避免仅为形式整洁制造大量单函数文件。
- 依赖方向可解释。公共层不应任意反向依赖部署细节；跨层通信通过明确接口、协议或受控适配点。
- 修改一个功能时，尽量局部完成；需要跨层修改时，边界和影响路径应可追踪。

**审查证据**：模块职责图、调用图、导入关系、重复实现位置、一次真实需求变更所涉及的文件与测试。

### 2.4 复杂度、抽象与删除能力

- 采用足够解决当前问题的最简单结构；抽象为消除真实重复、隔离变化或形成稳定契约服务。
- 对新接口、工厂、管理器、策略对象、适配层、缓存和兼容分支，要求明确调用者与实际收益。
- 发现新旧实现并存时，查明是否存在仍在使用的消费者；对无合同负担的旧路径应考虑删除。
- 评估新增功能时同时问“有哪些现有代码可以合并、替换或删除”。
- 不以重复代码行数机械决定是否抽象。两段恰好相同但未来变化原因不同的逻辑，未必应该耦合。

**常见症状**：一条业务调用穿过许多无意义包装层、多个并存的配置入口、为尚未发布的接口保留几代兼容、修改一项逻辑需同步调整多处。

### 2.5 硬编码、默认值、可移植性与演进

先识别数值或判断属于哪一类：

| 类别 | 例子 | 合理处理 |
| --- | --- | --- |
| 业务/协议不变量 | 协议允许的值域、消息格式 | 明确约束、集中定义并验证 |
| 部署参数 | IP、端口、设备路径、国家地区、输出设备 | 合理默认值 + 配置或发现机制；明确校验 |
| 安全策略 | 访问权限、受信任边界、秘钥处理 | 在可信层执行，默认安全；不能由不可信输入任意关闭 |
| 依赖与兼容契约 | 依赖版本、线上 API、数据库结构 | 锁定可复现版本，明确支持范围与升级路径 |
| 偶然的环境事实 | 某台开发机路径、特定 USB 枚举序号 | 避免硬编码，改为能力探测或可配置的显式绑定 |

不是任何数字都该变成配置项。新增配置也带来验证、文档和状态组合成本。

**关键提问**：该限制的依据是什么？谁有权修改？变更需要改代码、改配置还是改设备？失败时应拒绝、降级、重试还是明确提示？

对依赖升级：锁文件本身通常是可复现性工具；真正的问题是从不升级、不可测试升级，或把某个旧版本的偶然行为当作永久契约。

### 2.6 安全与必要防御

- 明确不可信输入、鉴权与授权边界、敏感数据、秘密来源及跨进程/网络的信任关系。
- 验证应放在责任明确的边界；内部已被可靠约束的数据不必每传一层就重复做同样的校验。
- 安全失败默认拒绝，错误信息不泄露敏感内容；公开例外必须有明确定义。
- 不自行实现成熟、安全敏感的协议或密码学功能，除非有充分理由及额外验证。
- 异常处理不能把授权失败或数据不一致伪装为成功；记录可操作的故障信息。
- 不因为“安全”二字接受任意固定路径、机器型号、版本或无根据的拒绝条件。安全规则应对应可描述的威胁。

**审查证据**：威胁场景、信任边界、攻击或误用路径、现有框架能力、公开 API 合同、测试与运行结果。

### 2.7 错误处理、可观测性与恢复

- 错误类型与处置策略一致：立即失败、有限重试、降级、恢复、交由上层处理；不无条件吞异常。
- 日志对定位有价值：指明组件、动作、结果和必要的关联标识；不泄露凭据、个人数据或过量原始内容。
- 健康检查与真实服务能力一致；避免测试替身比真实服务返回更多字段，掩盖合同不一致。
- 重试设置明确上限、退避、取消和幂等性；自动恢复有可验证的成功条件。
- 初始化、运行、退出、重启后恢复等生命周期行为可观测，关键资源能够释放。

### 2.8 性能、内存和实时性

- 先定义目标设备与负载，再决定性能预算和优化方向。
- 采集 CPU、常驻/峰值内存、启动耗时、吞吐量、平均与尾部延迟、抖动、缓冲下溢、资源泄漏和长时间运行表现。
- 优先定位热点和重复工作；避免无效轮询、无界队列、不断增长的缓存、重复解析、频繁分配或不必要的同步阻塞。
- 对实时链路，稳定的时延和抖动通常比平均吞吐量更重要；一项优化不能以破坏正确性或可维护性为代价，除非收益有证据且权衡明确。
- 静态阅读只能形成性能假设，不能替代目标环境下的基准测试、性能剖析或负载测试。

### 2.9 并发、状态与资源生命周期

- 清楚标明状态所有者，减少共享可变状态；锁、线程、协程、任务和回调的交互可解释。
- 检查竞争、死锁、消息乱序、阻塞、取消传播、资源释放和 shutdown 顺序。
- 文件句柄、socket、进程、线程、设备及缓冲区的创建和释放对应；异常路径也释放资源。
- 不为了形式上的“线程安全”引入多余锁，也不因为已有局部锁就推断全链路安全。

### 2.10 依赖、构建、部署与运行环境

- 每个外部依赖有具体用途，不重复引入功能重叠的库；版本范围、许可和更新责任清楚。
- 构建与部署可以复现，部署时的配置与源码分离；本地测试、CI 与目标设备之间的差异被明确记录。
- 不默认目标系统具备开发机上的路径、字体、音频设备、系统服务、shell、网络或管理员权限。
- 使用明确的初始化、升级、回滚和状态迁移流程；失败时给出诊断信息，不留下难以恢复的半完成状态。
- 对硬件、驱动和操作系统接口，区分可探测能力、必须匹配的合同与尚未验证的兼容性。

### 2.11 测试、文档和可维护交接

- 单元测试验证局部行为，集成测试验证真实边界与接口，端到端测试验证关键用户流程；不能用一种测试伪装成全覆盖。
- 测试使用合理的替身，不得改变关键合同、权限和错误语义；验证测试在故意破坏相关行为时确实会失败。
- 重要修复有回归测试或其他可重复的验证步骤；非确定性测试应治理而非长期忽略。
- 记录运行方法、配置项、外部合同、已知限制和重大设计理由；避免重复源码、自动生成没人维护的长篇文档。
- 提交和审查范围清晰；功能改动、纯格式整理、重构、依赖升级尽量分别进行，便于回归、定位与回滚。

### 2.12 可演进性和团队所有权

- 实际修改、排错和升级时，维护者能够找到负责位置，解释行为和约束，不依赖某个人的记忆或 AI 对话记录。
- 稳定公开合同有明确兼容政策，内部实现没有消费者时可以简化或替换。
- 缺陷修复应改善相应的测试、观察能力或工程约束，降低同类缺陷重复出现的概率。
- 代码规范支持持续维护，不鼓励为满足指标而制造仪式性文件、类、注释、测试或审批。

## 3. 反模式清单：症状不等于定罪

| 症状 | 常见风险 | 必须核对的合理例外 |
| --- | --- | --- |
| 相同逻辑多处出现 | 漂移、漏改、合同分叉 | 是否刻意隔离不同变化原因或兼容不同协议 |
| 巨型函数/类 | 职责不清、难测试、影响范围大 | 是否为可连续阅读的算法或必要状态机 |
| 很多一行函数和间接调用 | 跳转成本、控制流不透明 | 是否封装有语义的公开接口或真实边界 |
| 长名称、重复前缀 | 信息噪声、难阅读 | 是否需要在远距离作用域避免歧义 |
| 过多注释 | 事实重复、过期、误导 | 是否解释外部协议、算法或隐含约束 |
| 魔法数字/固定路径 | 环境耦合、无依据限制 | 是否为稳定的协议常量或安全不变量 |
| 大量 try/catch 与默认值 | 吞异常、假成功、掩盖缺陷 | 是否属于明确规定的容错边界 |
| 层层兼容和回退 | 架构膨胀、长期维护成本 | 是否存在真实用户、线协议或迁移期合同 |
| 测试很多且都通过 | 可能验证错对象、替身过宽 | 测试是否能发现真实合同被破坏 |
| 代码非常短或性能极高 | 可能难懂或不安全 | 是否有必要的性能证据和清楚的约束 |
| 依赖版本被锁定 | 可能过时但也保障复现 | 是否有明确的升级、漏洞检查和兼容验证机制 |

严禁把上述症状直接等同于缺陷。结论必须说明上下文、实际损害和反证检查结果。

## 4. 严重度、证据与决策

### 4.1 严重度（优先级，不是代码丑陋程度）

- **P0 阻断**：已证实的高危越权、数据损坏、不可恢复的严重故障等，需要立即止损。
- **P1 高**：有可信复现或强证据的关键功能错误、关键部署失败、严重稳定性或安全风险。
- **P2 中**：具体可验证的结构负担、重复实现、环境硬编码、重要测试缺口或性能问题，已影响或很可能影响维护与可靠性。
- **P3 低**：局部命名、注释、格式、低风险小范围整理，优先随相关修改处理。

优先级可结合影响、发生可能性、暴露范围、修复成本及验证难度调整；不采用“每一条规则违反一次就扣分”的机械评分。

### 4.2 证据状态

- **已验证**：能提供明确源码位置和复现、测试、实测或可闭合的执行路径。
- **高可信推断**：静态证据充分，但尚无运行验证；需说明尚缺的证据。
- **待调查**：存在症状或推测，需要补充环境、业务合同或调用者信息。
- **已排除**：有反证说明该候选在当前约束下合理。

“未发现问题”“尚未检查”“环境不足无法验证”必须分开。不要将推断写成实测事实。

### 4.3 单条发现必须包含

1. 唯一 ID、分类、严重度、证据状态。
2. 问题所在文件与具体行/符号，并指出受影响的调用者或功能。
3. 期望行为、实际行为或结构症状。
4. 证据：调用链、配置、测试、日志、性能数据或正式合同。
5. 影响：错误结果、风险、额外维护成本及触发条件。
6. 已检查的反例与合理例外；不确定性。
7. 最小合理修复方向、回归验证方式；必要时明确“不建议修改”。

对安全关键、高风险跨层或性能结论，至少补充一次独立验证：重现、另一条调用路径、原始协议核对或目标环境测试。

## 5. 让 AI 学会执行标准

这里的“学会”主要指**在当前任务中得到可检索的标准和证据，遵循稳定的审查流程，并通过校准案例证明它会正确判别**。不能假设把文档发给 AI 一次，它就完成永久的模型训练或未来自动记住全部细节。

### 5.1 四层知识来源

1. **通用原则**：本文件定义的质量维度、证据要求、禁止机械打分与误报控制。
2. **项目事实**：当前有效需求、公开 API、协议、设备、部署环境、性能预算、测试命令和已批准架构；这些是项目事实的来源。
3. **当前源码**：真实实现、调用关系、依赖、测试和配置；它可能违背规范，也可能揭示文档过期。
4. **校准样本与历史结论**：已证实缺陷、已排除的合理实现、常见误报、修复后回归案例。

遇到冲突时，记录来源和差异，不直接把任意一方当成事实。特别是仓库中某种写法出现很多次，不等于它就是值得继续复制的规范。

### 5.2 规则的表达结构

每条可执行规则采用：**适用范围 → 要防止的风险 → 判断条件 → 合法例外 → 需要的证据 → 可能的验证方式**。

示例：

> 规则：在设备发现和部署模块中，检查是否把开发机上的固定设备索引当作运行时唯一选择。若用户部署需要跨设备复用，且设备可动态枚举，应优先调查能力发现或配置。协议标识、已明确绑定的设备以及测试夹具中的固定值是合法候选例外。指出真实入口、配置调用链和目标环境的约束；缺少硬件时只报告待验证风险。

这样比“禁止所有硬编码”更可执行，也不容易误伤真实的协议常量。

### 5.3 校准集：同时检查识别能力和克制能力

| 案例 | 理想判定 | 原因 |
| --- | --- | --- |
| 运行时写死开发机的设备序号，部署目标会变化 | 候选问题；核对实际部署与发现能力 | 可能产生环境耦合 |
| 协议限定的最大值定义成常量 | 通常不报 | 真实合同固定 |
| 应用锁文件固定依赖版本，另有定期升级机制 | 通常不报 | 可复现构建是合理目标 |
| 未公开内部接口保留三代兼容，但没有消费者 | 候选结构负担；证实消费者后决定 | 避免无意义兼容 |
| 公开接口在生产已有旧客户端 | 不应简单建议删除兼容 | 保持契约 |
| 鉴权由可信中间件完成，处理函数未再重复验证 | 不应直接报越权 | 必须追踪实际请求路径 |
| 几个文件重复实现鉴权策略且已有分歧 | 重要候选问题 | 有真实策略漂移风险 |
| 静态阅读怀疑有较大 CPU 消耗，但没有性能测量 | 待验证，不写“已经很慢” | 不能用猜测替代实测 |
| 复杂算法旁有长注释，解释推导与外部约束 | 通常保留 | 有信息增量 |
| 修改一行缺陷却连带重排大量无关文件 | 报审查范围失控 | 增加回归及回滚难度 |

建立校准集时至少包含**应报、应忽略、应暂缓**三类；既计算找到了多少真实问题，也计算误报数、优先级是否合理、证据是否完整。只有准确率而没有误报和证据检验，会鼓励 AI 把所有疑点都报出来。

### 5.4 工具分工

- **确定性工具**：编译、类型检查、格式检查、静态分析、安全规则扫描、依赖审计、单元/集成测试和性能工具。工具能客观判断的事项优先由工具判定。
- **AI**：理解调用链、分辨职责边界、发现重复逻辑与不合理兼容、提出实验、解释上下文、整理证据和权衡方案。
- **人**：确认业务合同、真实设备约束、安全取舍、优先级和需要实际更改的范围。

AI 不能以自己的第二次同样判断代替外部验证；应尽可能引用独立证据。

### 5.5 不膨胀的仓库集成

不要把这份完整标准复制进 `AGENTS.md`。后者保留项目目的、导航、边界、必要的测试入口及指向完整规范的路径。按任务读取有关章节，项目特殊规则按相关模块放置。

可在现有仓库说明中增加类似简短入口（仅为模板，不要求立即修改任何仓库）：

```markdown
## 代码质量

需要进行全库质量审查、架构审查或重要重构时，读取
`docs/code-quality-ai-audit.md` 的相关章节。
审查时区分已证实缺陷、推断和待验证风险，检查合法例外；
不得仅凭函数长度、重复行数或固定常量认定问题。
```

## 6. 存量代码库审查：全流程

### 阶段 A：确认边界与基线（只读）

1. 记录版本/提交、分支、工作区是否已有更改、审查日期、可用环境以及不能验证的设备或依赖。
2. 确认需要审查的功能和模块清单；生产、生成代码、第三方依赖、测试与脚本分别分类。
3. 收集需求、协议、部署说明、项目说明、已有报告和约束，不把缺失信息默认为不存在的要求。
4. 明确本次只做审查还是允许修复。只读审查不得改源码、测试、配置、依赖、提交或部署。

### 阶段 B：建立可定位的结构图

1. 从入口与用户功能出发，确定每项功能的调用路径、关键状态和依赖。
2. 标出进程、模块、网络、IPC、数据库、文件、设备和外部服务边界。
3. 为每条功能路径记录主要实现位置、测试、配置来源及已知外部合同。
4. 识别代码中可能存在的多实现、循环依赖、跨层绕行、散落状态、废弃路径。

**产物**：功能—入口—执行模块—状态所有者—外部依赖—测试的映射；不要求为了漂亮而画无用的全量依赖图。

### 阶段 C：运行现有验证手段

1. 使用项目已公布或明确可推导的构建、测试、格式、类型、安全和依赖检查命令；记录环境与完整结果。
2. 先报告现有失败，不将其归咎于本次尚未发生的修改。
3. 如果测试、扫描或脚本会修改生产数据、部署、推送、安装系统服务或接触真实设备，先确认其副作用和授权范围。
4. 需要硬件的性能、时序、音频、网络或设备兼容测试，明确模拟与实机证据的不同可靠性。

### 阶段 D：逐维度审查

根据第 2 节的十二个维度进行。重点查看：

- **入口与契约**：鉴权、配置、公共 API、状态更新、异常、重试和兼容。
- **结构与可修改性**：重复、横跨模块、职责模糊、耦合、过度抽象、历史路径。
- **外部变化**：设备、操作系统、库升级、网络、地区、权限与部署方式改变。
- **资源和生命周期**：线程、队列、句柄、缓存、进程、锁、启动和退出。
- **测试质量**：模拟与真实合同的一致性、误报/漏报、回归用例是否有效。

针对每个候选问题，必须沿调用链验证影响范围，并主动搜索其合理例外与反证。

### 阶段 E：挑战式复核

对 P0/P1 和跨模块结构结论执行第二轮核查：

1. 列出首轮结论依赖的假设。
2. 搜索使结论不成立的证据，例如真实消费者、协议约束、框架保证、合法兼容、部署说明。
3. 区分必要重复与无意义重复、必要防御与无效防御、需要锁定的版本与不合理环境锁死。
4. 对无法确认的项目降为待调查，不以“可能有风险”写成确定缺陷。
5. 审查报告自身是否有重复发现、相互矛盾的修复建议、跨层遗漏和过度修复。

### 阶段 F：生成报告与完成条件

按第 7 节格式整理。报告可完成的前提是：

- 审查范围覆盖情况、排除项和未检查区域都明确；
- 每个实质发现都有可定位的证据；
- 重要风险做过反证检查；
- 静态推断与实机、自动化测试结果分别标记；
- 修复建议能被分阶段执行，不要求一次性重写全库；
- 未经授权不修改任何业务文件。

### 阶段 G：后续修复和持续监督（另行授权）

1. 按风险、依赖顺序、影响范围和验证成本排序；先恢复可重复验证能力，再处理结构改动。
2. 每个修复尽量保持一个明确目标，给出预期变化、回归测试和回滚方法。
3. 对已确定的错误增加行为回归测试；对性能问题保留优化前后同环境数据。
4. 清理不再需要的兼容层、重复代码和失效注释；避免修复只会让代码继续增长。
5. 将经证实、普遍、长期有效的经验写回规则或校准集；无效规则及时删除。

## 8. 可直接用于 Codex 的审查任务指令

> 将本文件提供给 Codex，或把它放在仓库文档中并指明路径。以下指令不依赖某个具体项目名。

```text
请根据《高质量代码标准与 AI 代码审查协议》，对当前仓库做一次只读的代码质量基线审查。

目标是判断代码是否正确、可理解、可定位、可修改、可验证，能否适应真实部署变化，并在性能、内存、并发、安全、错误处理、依赖和可维护性上满足项目约束。覆盖标准中的全部质量维度，不局限于某几项。

先识别仓库指令、需求、架构、实际入口、部署环境、外部协议与现有测试。以真实功能路径建立结构映射，区分规范、当前实现、历史兼容和未知事实。记录基线版本、已有变更和可用验证条件。

执行适当的只读检查和安全的现有测试；对会写入生产数据、联网变更外部状态、安装服务或影响实机的操作，不在未获授权时执行。此次不得修改源码、测试、配置、依赖、文档、提交、分支或部署状态。

逐项检查命名、注释、目录与模块组织、职责和依赖、重复实现、过度抽象、无用兼容、硬编码、默认值、配置和环境耦合、可移植性、安全边界、防御性代码、异常与重试、可观测性、状态与并发、资源生命周期、性能内存实时性、测试有效性、构建部署以及长期演进成本。

每项候选问题都要追踪调用者及实际影响，并主动寻找合法例外和反证。不要因为函数长、出现常量、存在重复或依赖被锁定就直接认定为缺陷。不要把静态猜测伪装成运行结果。对没有足够证据的结论标记“待调查”。

重点识别那些虽然现在能运行，但导致功能散落、修改范围扩张、环境变化后失败、无意义防御与兼容、依赖升级困难、故障被吞掉、性能隐患无法验证的结构性问题。也应识别可以删除、合并、替换的冗余代码，而不只建议增加层次、测试或配置。

输出统一格式的审查报告：基线与范围、功能结构映射、逐项发现及文件位置、影响、证据、反证、优先级、待验证项、覆盖核对、按依赖顺序排列的最小修复建议。对 P0/P1 和重大跨层判断进行挑战式复核。不要将所有风格偏好列成高优先级问题，也不要以一个总分代替证据。

此次只审查、不修复。完成后等待明确批准再进行任何代码修改。
```

## 9. 减少 AI 漏报、误报和规则退化

每次完善审查能力，至少回答：

1. 是否发现了故意放入的真实错误（召回）？
2. 是否放过了合理常量、合法兼容、框架自带的验证和无害重复（克制）？
3. 是否仍能发现与特别规则无关的普通缺陷（普遍审查能力）？
4. 每条发现是否可定位、可验证、可排序、可修复（行动价值）？
5. 规则自身是否已经过时、与其他指令冲突或导致输出膨胀？

校准记录最好保留最小化的前后源码片段、真实标签、判断依据和 AI 输出，不需保存完整敏感代码。要测试多个改动同时出现的情况，也要测试完全没有问题的变更。

对于编程 AI 的“自我审查”，应额外检查：是否偏袒自己提出的设计、是否因为前文已有结论而忽略反证、是否把格式问题当成架构问题、是否以增加代码来消除所有疑点。

对新增规则执行三个案例：违规、合法例外、无关改动。若规则只带来泛泛提醒或大量误报，就缩小范围或删除。审查标准应随已验证经验演进，而不因每一次 AI 犯错就无条件增加永久限制。

## 11. 维护原则

- 本文应长期保持技术栈中立；项目专属事实放项目文档。
- 增加规则前先确认是否已有类似原则；合并重复表达。
- 有事实依据、示例、例外和验证办法的规则优先；删除空泛口号。
- 工具、模型、库和部署环境发生变化时，复核对应流程，不让旧的假设长期固化。
- 报告是某个版本的观察结果，不会因为模型更换而自动成为永久事实。
- 审查与修复是两个独立授权阶段；修复以真实的测试、性能和可靠性收益为验收依据。
