# Effect parameter modulation (internal Show v2)

`parameter_modulation` is an internal Show/YAML authoring feature evaluated by the RK3588 runtime. It is
not part of Host API V1 and is not advertised to the APP. Existing `audio_modulation` remains the separate,
compatible owner of common cue `brightness`, `speed`, and `intensity`.

## Authoring shape

The cue field is a non-empty list. Every target may appear at most once:

```yaml
parameter_modulation:
  - target: contrast
    mode: modulate
    source: audio.bass
    output_min: 0.8
    output_max: 1.5
    smoothing_seconds: 0.10
```

Only a fixed effect may use this block. `target` must resolve in that effect's live Registry metadata to a
`ParameterSpec` with `kind: float`, `runtime_mutable: true`, and `modulatable: true`. The loader rejects
common `brightness`, `speed`, and `intensity`, non-float values, unsafe floats, duplicate targets, and all
adaptive-effect bindings. The authoritative current list is generated by
`scripts/export_authoring_contract.py`; do not copy a separate effect table into a Show tool.

## Modes

- `modulate`: `final = authored_base * mapped_multiplier`. The target must exist explicitly in
  `effect.params`. If its source is unavailable and `fallback` is omitted, the authored base is restored
  immediately and smoothing history for that binding is cleared.
- `drive`: `final = lerp(output_min, output_max, normalized_source)`. An audio source can be absent, so it
  requires a `fallback` final target value. `cue_progress` is always present and does not require fallback.

For either mode, an authored `fallback` is in the same mapped output domain: multiplier for `modulate`, final
parameter value for `drive`. It must lie inside `output_min..output_max`. An explicit fallback participates in
smoothing; an implicit modulate fallback restores the authored base without lag.

The loader validates every Cartesian endpoint/fallback combination through the selected effect's live
Registry validator. Runtime values are validated again immediately before effect render. This covers scalar
bounds and cross-parameter relations such as `highlight_gain >= base_gain`.

## Sources and normalization

Naturally normalized sources are `cue_progress`, `audio.rms`, `audio.loudness`, `audio.bass`, `audio.mid`,
`audio.treble`, `audio.spectral_flux`, `audio.onset`, `audio.peak`, and `audio.spectrum[0]` through
`audio.spectrum[15]`. A legitimate zero remains zero; unavailable audio is tracked separately so fallback
behavior is deterministic.

The raw-domain sources `audio.raw_level`, `audio.dominant_frequency`, and
`audio.dominant_magnitude` require finite `input_min` and `input_max`, with `input_max > input_min`:

```yaml
parameter_modulation:
  - target: contrast
    mode: drive
    source: audio.dominant_frequency
    input_min: 80.0
    input_max: 1200.0
    output_min: 0.5
    output_max: 2.0
    fallback: 1.0
```

Raw normalization is `(value - input_min) / (input_max - input_min)`, clamped to `[0,1]`. There is no global
dominant-frequency normalization and no expression or evaluation language.

## Smoothing and lifecycle

`smoothing_seconds` defaults to `0`. Positive values use cue delta-time and the exponential coefficient
`1 - exp(-delta_time / smoothing_seconds)`, making the same elapsed interval equivalent at 30 and 60 FPS
within floating-point tolerance. State is private to each cue/branch, reset clears it, and replay reconstructs
it. A `pre_roll` branch renders while hidden and consumes the real historical `AudioFeatures` passed to each
frame; no audio history is synthesized.

Application order is: authored effect params and existing compositor color handling, then
`parameter_modulation`, then Registry validation, then effect render. Existing common `audio_modulation`
continues to compose cue brightness/speed/intensity through its prior path.

All runtime and physical behavior remains **NOT HARDWARE VERIFIED**.
